# 松伴 AI 学习产品 Constitution

> 范围说明（2026-10-31）：当前项目协作工作台按已获用户授权的[项目工作台宪法](../../docs/planning/项目工作台宪法.md)执行；本文件的家庭学习产品原则仍为原草案。工作台 React 静态挂载是现有统一前台的局部适配，不代表采用第二套前台或启动家庭学习产品实现。

适用范围：从零开始、逐步深入 AI 工具、模型与 API 实验的家庭学习产品。
这是按 Spec Kit 结构建立的首版项目宪法草案。编写日期为 2026-10-30，
代码事实基线为 `9b92738`；条文中的“必须”“不得”是采纳后的工程与产品要求，
不表示当前代码已经具备这些能力。

## Core Principles

### I. 家长购买价值，孩子获得可观察的学习进步

首轮产品必须以“不懂 AI、不知道孩子可以尝试什么”的家长为购买决策者，
以孩子为主要学习者。机构可以是后续渠道，不能在没有明确方向修订的情况下替代首轮用户。
每个功能规格必须说明服务的用户、具体困难、可观察结果和验证方式。
家长付费意愿、价格、续费与获客成本均是待验证假设，不得写成已有商业结论。

年龄与自选“小白／有基础／大神”只能用于内容表达和起点推荐；
推荐必须允许调整并结合短任务证据。不得把年龄当能力、把自选身份当测评结论，
也不得为了注册强迫零基础用户填写虚构技能或工作画像。

### II. 课程必须让学习者操作、解释、修正和迁移

每个可发布学习单元必须同时具备学习目标、可执行任务、材料、帮助层级、
检查依据、失败后的补练路径和完成证据。AI 代做、模型调用成功、观看完成或作品好看，
均不能单独认定掌握能力。

学习结果必须区分孩子的选择与修改、AI 或家长帮助、自动检查、人工复核及未观察事项。
独立迁移任务必须记录新材料、帮助情况和实际表现；平台内迁移不得宣传为已掌握外部工具。
修改内容后必须产生新版本，失败与帮助历史不得被覆盖为“独立完成”。

### III. 身份、家庭数据和模型凭据必须隔离

后端必须验证每个资源所属家庭、学习者与当前操作权限；隐藏按钮不构成授权。
孩子会话不得购买、管理家庭、发布课程、人工核验订单或增加模型预算。
切换到学习会话时必须撤销当前浏览器可直接使用的家长管理会话，
返回家长管理必须重新认证；切换身份时前端清除私有缓存并丢弃旧身份的迟到响应。

真实供应商密钥只允许在服务端受控凭据系统使用，不得出现在前端、课程配置明文、
日志、仓库或导出成果中。新学习链路不得直接复制旧个人模型密钥存储方案。
默认仅收集本阶段所需年龄信息，不收集无关精确生日、学校或隐私材料。
家长报告的原始对话可见范围、数据保留及删除规则必须在试点前明确并落地。

### IV. 模拟、真实运行与回放必须真实可辨

所有实验必须保存并返回 `mode=mock|live|replay`。
模拟不调用真实供应商、不消耗真实调用额度；回放关联原运行与原时间，不伪装成新调用。
真实运行必须经过课程授权、模型配置白名单、家长授权及额度检查。
用户必须能知道当前模式、结果来源和用量是否已确认，但呈现方式由设计与前端决定。

运行记录必须包含请求模型、实际响应模型（未知为 null）、配置版本、输入与材料版本、
耗时、用量来源及截断信息。只有两个实际可用且本次确实参与的不同模型才可称“模型比较”；
同模型不同提示或参数必须称配置／提示比较。未知成本不能记作零成本。

### V. 学习记录、运行和成果必须可恢复、可追溯

运行、额度预占、候选作品、检查、提交和报告均必须持久化。
刷新、重登或服务重启后从服务端恢复，不以浏览器缓存或进程内线程作为唯一事实来源。
已保存输入、课程材料、检查规则、帮助记录和成果之间必须保留版本关联。

超时不能自动等同失败。已经可能发出的上游请求进入 `unknown` 时必须有核对截止时间、
责任人、额度处理规则和关闭核对的出口。没有上游幂等保证时不得承诺外部严格只执行一次。
未知结果不得触发自动重复调用，报告重建也不得重跑实验。

### VI. 契约约束行为，设计保留 UI 决策空间

前后端必须遵守下节接口规范及其详细附件；后端是权限、进度、额度和结果状态的权威。
设计不得自创服务端成功状态，前端不得伪造成功、通过、付款到账或学习进步。

本宪法不规定颜色、字体、布局、导航形式、页面数量、组件名称或前端框架。
美术与前端可提出并迭代方案，只要用户能理解任务、模式、状态和下一步，
且关键操作在约定设备、键盘操作及错误状态下可完成。
设计交付必须包含可编辑来源、状态与交互说明、素材授权、版本和验收依据；
截图或单张成功态效果图不能单独构成可开发交付。

### VI-A. 统一前台采用 design-v1 视觉契约

原则 VI 保留设计探索空间；一旦项目在统一前台范围内采纳 `design-v1`，
该视觉契约对实现具有强制约束。design-v1 以参考页面
[`#/event`](https://songban-hackathon-preview-20261030.social-cat-4573.chatgpt.site/#/event)
为基准，统一页面壳、活动／实践信息架构、语义 tokens、组件状态和响应式验收。
具体条款见[统一前台视觉宪法与 UI 契约](../../docs/planning/视觉宪法与%20UI%20契约.md)。

统一前台必须使用暖米白背景、紫色主行动、统一品牌栏与导航；实践通道承载团队现场、
方向、任务、个人工具、资料库、成员、交付和复盘。不得在统一前台继续新增旧深色后台视觉，
不得用 iframe 作为最终整合方案。组件必须覆盖默认、悬停、键盘焦点、禁用、加载、空态、
错误和未知状态；成功、通过、提交、付款和学习结果只能由后端事实驱动。

本条不改变 API、权限、数据状态、身份边界或历史兼容入口，也不把视觉验收当作业务验收。

### VII. 先交付最小完整学习链路，再扩大功能

首轮必须以一个可完成、可检查、可解释并能向家长反馈的项目验证闭环。
首个候选项目为短资料问答助手；具体材料与课次长度由教研及试用收口。
真实模型首轮限受控文本实验，完整桌面系统、任意终端执行、任意外部 API、
开放密钥输入和全面多模态不属于默认首轮范围。

实现必须区分复用、改造与新建，并记录影响及回退办法。
新学习域不得把历史团队任务表、两行资料库或旧能力画像直接解释成学习证据。
现有团队协作系统的接口与默认入口是否迁移必须另有实施方案；
本宪法的建立不自动修改旧系统运行行为。

### VIII. 用可复核证据判断质量与商业进展

每次交付必须说明已经实现、仅模拟、尚未实现和实际验证范围。
静态代码审阅、契约 fixture 测试、真实模型联调、真实家庭试用分别记录，不能相互替代。
不得把自动化测试通过写成孩子学会，也不得把路演演示、购买意向或人工开通写成收入验证。

质量检查聚焦越权、密钥、版本冲突、重复运行／扣额、失败恢复和学习证据真实性等实际风险。
普通可逆文案与视觉调整不要求机械地新增测试。
商业验证必须记录真实触达、启动、完成、报告理解、付费／退款和后续学习，
同时记录模型及人工辅导成本，避免只看漂亮的总完成率。

### IX. 课程与服务必须有人负责

教研负责目标、材料、检查规则和反馈有效性；产品负责范围、权益与商业验证；
运营负责人工开通、异常核对、复核排队与用户反馈。
这些责任不得默认转给前端或美术，也不得用模型输出替代具名的人工决定。
首轮允许一个人兼任多角色，但发布记录必须标明实际责任人和处理入口。

## 接口规范（强制）

本节直接属于宪法约束，不是可选建议。详细路由、字段、例子和联调场景见
[前后端接口规范](../../docs/planning/前后端接口规范.md)。该附件的初版为 `1.0.0-draft`，
实施时维护对应 OpenAPI；附件和 OpenAPI 的差异必须消除后才能宣告接口验收。

### 1. 版本、边界与字段语义

1. 新学习域统一采用 `/api/learning/v1`。它是拟新增命名空间，不表示当前已存在。
   旧规划的 `/api/learn` 仅为未实施草案示意，统一由本版替代；
   现有 `/api/core`、`/api/studio` 的行为和格式不得被本规则静默改变。
2. 传输使用 HTTPS、UTF-8 JSON；JSON 字段为 `snake_case`。
   标识符为服务端产生的不透明字符串，时间为 UTC ISO 8601，版本为正整数。
   金额使用最小货币单位整数及币种；未知数据为 `null` 并附来源／状态，不用零或空串伪装。
3. 每个接口必须定义调用身份、必填／可空字段、取值范围、响应、错误、幂等及权限边界。
   新增可选字段可以兼容扩展；删除／重命名字段、改变含义或状态语义必须版本化并给出迁移期。
   未识别状态在客户端显示“待确认／暂不可操作”，不得兜底成成功。

### 2. 身份与请求防护

1. 新学习 Web 会话使用服务端会话及 `HttpOnly`、`Secure` Cookie。
   所有有副作用请求校验 CSRF token 和允许的来源；禁止把高权限 token 放入浏览器持久化存储。
   `GET session` 返回当前主体与可做动作，前端不能提交角色字段给自己升权。
2. 家长、学习者和受限运营身份分别授权；资源访问逐项检查归属与权限。
   对跨家庭或不应暴露存在性的资源统一返回 `404 resource_not_found`，
   对已知但不允许的动作返回 `403 forbidden`；两者均不得泄露他人数据。
3. 进入学习模式、回家长管理、退出、会话过期均有明确的服务端状态变化。
   会话 Cookie、密码、短信码、模型凭据和 CSRF token 不得进入普通日志或报告。

### 3. 成功、失败与状态码

成功响应固定包含 `data` 与 `meta.request_id`；失败响应固定包含
`error.code`、`error.message`、`error.retryable`、`error.details` 与 `meta.request_id`。
`message` 是可给用户看的短说明，堆栈、上游凭据及内部诊断仅写入脱敏日志。
分页使用 `data.items`、`data.next_cursor`；空列表与读取失败必须区分。

HTTP 约定：`200` 成功读取／更新，`201` 创建，`202` 已接收异步任务；
`400` 格式不合法，`401` 需要认证，`403` 无权，`404` 不可见／不存在，
`409` 幂等正文冲突、版本冲突或非法状态迁移，`422` 字段／课程约束不满足，
`429` 限流或真实额度不足（必须用不同 `error.code` 区分），`503` 暂不可用。
不得用 HTTP 200 包装业务失败。运行查询 HTTP 200 可以返回 `status=failed`，
因为查询本身成功；前端必须继续判断资源状态。

### 4. 并发、幂等与重试

草稿、个人配置、订单核验等可变资源必须携带 `expected_revision`。
不匹配返回 `409 revision_conflict` 与当前 revision，客户端读取最新数据并保留未保存草稿，
不得自动覆盖。字段保存成功返回新的 `revision`；模型输入另有 `input_version` 与 `input_hash`。

创建实验、作品候选、检查、定稿、订单及运营核验等有副作用操作必须携带
`Idempotency-Key`。服务端将键绑定主体、操作、资源和规范化正文摘要：
同键同正文返回原资源；同键不同正文返回 `409 idempotency_conflict`。
建运行记录和预占额度必须在同一原子事务完成，不能只在前端禁用按钮。

读取可有界重试并遵守 `Retry-After`。写请求不得换新键自动重放；
网络断开时先按原键／资源查询，仅可用原键和原正文恢复原操作。
真实上游是否已执行不明确时，不得因重试客户端请求而再次发出上游调用。

### 5. 实验与额度的强制状态契约

实验执行状态只有 `queued|running|succeeded|failed|unknown`。
查询必须区分执行状态、核对状态与额度结算状态，不能合成一个“完成”。
`unknown` 配套 `review_due_at` 和 `reconciliation.status`；
有可靠证据才能改成功／失败，无法查证时可关闭核对但仍保留执行未知。
额度必须按已声明规则释放或调整，不得无限冻结、重复扣额或把未知计为免费成功。

请求必须引用已经保存的 `attempt_id`、`input_version`、`input_hash`、
服务端允许的 `model_ref` 和参数；不得接收真实密钥、任意 URL 或前端传入的“已通过”结论。
输出必须包含模式、输入与课程版本、用量来源及截断状态；
前端用这些事实展示结果，不能依据动画结束或等待时长判断成功。

### 6. 作品、检查、定稿与报告的强制关联

顺序必须为：保存输入 → 创建不可变候选作品 → 对候选版本检查 → 提交同一候选。
候选使用 `artifact_id + artifact_version + content_hash` 唯一定位，
其中 `content_hash` 是后端计算的候选内容摘要，不能与输入摘要混用。
检查必须关联相同候选、测试版本及来源；`pending_review` 必须由授权人员处理。

定稿请求携带候选三元组、`check_ids` 与 `expected_revision`。
后端验证所需检查、孩子说明和迁移任务，再决定课次为
`passed|needs_practice|pending_review`。前端不能提交 `passed=true` 或直接改变进度。
修改候选内容必须生成新版本并重新检查，旧检查不能自动继承。

报告状态独立为 `pending|ready|failed`，引用成果、检查与帮助证据。
报告失败不撤销已保存成果；重建只能基于原成果事实，不能重跑实验或补造进步。
课程权益、真实调用额度、订单到账与学习结果分别保存并分别判断。

### 7. 契约交付与验收

接口交付必须包含版本化 OpenAPI、字段及枚举、脱敏请求响应样例、
权限与错误案例、变更说明及可重复的契约测试／fixture。
前端和后端共同验证至少一条真实端到端链路及其失败恢复，设计依据同一状态表交付。
mock fixture 仅证明契约和表现可实现，真实模型、运营及学习效果分别验收。
新增接口不能因“页面先做了”或“后端方便”而绕开本节。

## 开发流程与质量门槛

每个功能按 Spec Kit 的“需求规格 → 实施计划 → 任务 → 实现与验收”组织。
安装 CLI、写宪法和生成完整项目集成是不同动作；本次仅交付文档与宪法，
没有安装项目级命令、事件 hook 或生成实现代码。

1. **需求规格**：说明用户、问题、范围／非范围、正常与异常流程、可验收行为、
   学习证据、商业假设及数据边界。独立列出未决事项与收口责任，不能用假设冒充已确认。
2. **实施计划**：说明复用／改造／新建、数据与接口、依赖、风险、回退办法和验证方式。
   在研究前及设计后检查本宪法；不能用选框勾选代替符合性证据。
3. **任务拆分**：按可验收的完整用户故事拆分，并分别写产品／教研、前端、后端、
   美术、运营责任与交付物。美术交付与前端反馈需有共同版本和状态对照。
4. **实现与联调**：对身份越权、重复运行、额度一致性、版本冲突、重启恢复、
   候选与检查错配、报告失败等关键路径完成有意义的检查；记录执行环境和局限。
5. **试点就绪**：真实调用前明确供应商、预算和故障处理；家庭试点前明确教研、
   报告边界和复核人员；收款前落实价格、权益、核验、退款与数据保留说明。
   尚未验证的收费方案不能以正式承诺对外推广。

每份功能计划必须给出以下 Constitution Check 结论及证据位置：

- C1：是否解决首轮家长／孩子的具体问题，是否避免年龄与能力混同。
- C2：是否具备操作、解释、检查和迁移证据，是否真实记录帮助。
- C3：是否隔离身份、家庭资源和凭据，是否有越权验证。
- C4：是否区分 mock／live／replay、截断、未知用量与比较条件。
- C5：是否满足本宪法的接口、状态、版本、幂等及可恢复性规则。
- C6：是否交付全状态设计及协作依据，同时保留 UI 决策空间。
