## 结论

新生成的每项任务除原有字段外，还带一个 `execution`（照做说明），说明里有操作场景、步骤、给个人 AI 的指令、要交的成果和卡住时怎么求助。这些说明会沿用原流程一路保留：草案、队长确认、活动任务、成员的“我的任务”、个人插件读取、历史版本、交接导出，以及服务重启之后。

后端对说明做类型、数量、长度和空值校验，只要有一项任务不合格，整份草案就不采用，原计划不变，网页上显示错误。旧计划和旧草案能照常读取，页面和导出会明确写出“旧任务尚无操作说明”，不会补写。

验证全部在无 `.env` 镜像、合成账号和协议替身下完成：单元测试、真实 TCP 隔离验收（16 项）和不依赖浏览器的页面渲染检查都通过了。**真实浏览器没有实测**：Chrome 在当前沙箱内无法启动，浏览器脚本已写好但没有运行成功。**协议替身不代表真实模型的拆解质量**；本轮没有调用任何模型，不能宣称 AI 已经能可靠地拆出照做说明。

## 修订 1（监理复核后）：刷新时保留已展开的说明

问题：队友任何新记录都会让资料版本变化，页面整块重绘，已经展开的“照做说明”会自己收起，打断正在看步骤的人。本轮只修这个问题，没有做 CORE-03。

做法（只改 `static/core.js`，`static/core.html` 的脚本版本号改为 `20261029-8`；CSS、后端、连接器、队长确认都没动）：

- 页面内存里记一份“用户展开了哪些说明”，不写 localStorage，也不上传。
- 每份说明的标识由四部分组成：团队、计划范围（已确认任务用计划版本号，草案用草案 ID）、任务编号，以及说明内容的指纹（标题、负责人、`execution`、检查方法、依据、前置任务）。
- 重绘时，标识完全相同的说明保持用户上次的状态：展开的仍展开，用户明确收起的仍收起。任务状态、进展等其他内容照常显示最新值。
- 说明内容变了、计划换版、草案换了、团队换了，标识就对不上，新说明一律从收起开始，旧状态不会带过来。内容和 AI 指令文本框每次都按最新数据重新生成，旧内容不会盖住新内容。
- 切换团队时清空记录，切回原团队也不会恢复；退出登录时清空；当前页面不再显示的说明，记录会被删掉。
- 草案外层的“查看建议任务”折叠框用同样的规则（团队 + 草案 ID），否则里面的说明虽然展开，外层一收也看不到。
- 编辑保护没改：正在编辑输入框或表单有未保存内容时，页面仍然不重绘；全局 5 秒同步和任务数据更新都照常进行。

  - 新计划版本、新草案、换团队（包括再切回来）都不带旧状态；
  - 不再显示的任务，记录会被清掉；

## 修订 2（监理复核 R2）：保护期间暂缓的更新不再被吞

问题：原来的 `refresh()` 会先把新数据写进 `state.data`，再判断要不要重绘。如果这时正在编辑（或页面忙），就跳过重绘。可下一次轮询时版本号没变，`changed` 已经是假，于是即使用户移开了焦点，页面也一直停在旧内容上。修订 1 加的只读 AI 指令框会触发编辑保护，所以“复制指令时队友有新记录 → 移开焦点后仍显示旧任务”这条路径确实会发生。

做法（只改 `static/core.js`，脚本版本号改为 `20261029-9`；后端、连接器、CSS 都没动）：

- 新增页面内标记 `state.pending`。有效更新到来但正处在保护中（输入框聚焦、表单有未保存内容、`state.busy`）时，只记下“欠一次重绘”。
- 之后任何一次轮询，只要保护已解除，就用当时最新的 `state.data` 补一次重绘，然后清掉标记，即使服务器的版本号没再变；最迟在下一次 5 秒轮询时补上。保护期间连着来几次更新，也只按最新数据补画一次。补画只是读取后重绘，不发任何写请求。
- 每次请求记下发出时的团队和登录凭证。回来时如果已经切了团队或退出登录，这次结果直接丢弃，既不写入 `state.data`，也不重绘，旧团队的数据不会画进新团队。
- 强制刷新（切换团队、切换页面、手动刷新）、重新登录载入和退出登录都会清掉 `state.pending`。不在“团队现场 / 资料库”页面时，行为与原来一致，不做自动重绘。
- 编辑保护本身没改；全局同步照常进行，`state.data` 会照常更新为最新数据。草案是否已发布只取决于服务器返回的数据，补画不会把草案显示成已发布。

验证（都不是浏览器实测）：

- `node scripts/executable_tasks_render_check.cjs` 全部通过。原有的草案任务、确认任务、恶意 HTML 检查和修订 1 的展开/收起检查都还在。新增的 11 项检查直接调用真实的 `refresh()`，只替换网络请求，并把 `overview()` / `libraryView()` 的轮询重绘和整页 `render()` 分开计数，所以手动整页渲染不能冒充轮询补画。覆盖：
  - AI 指令框聚焦时有新版本，不重绘，但 `state.data` 已同步到最新；
  - 再来一次更新，仍然不重绘；
  - 失焦后版本号不变，补画一次，用的是最后那次数据；
  - 再轮询一次，不会重复补画；
  - 表单有未保存内容、`state.busy`、资料库页面这三种情况，都是保护时不画、解除后补画；
  - 请求还没回来时切换团队：旧团队的结果被丢弃；切换后的强制刷新只整页渲染一次，并清掉欠着的补画；之后轮询的是新团队，也不会补画旧数据；
  - 请求还没回来时退出登录：结果被丢弃，之后不再发请求；
  - 所有轮询都只读不写；
  - 轮询路径从不调用整页 `render()`。
- 反向验证：把 `static/core.js` 复制到临时目录，故意改坏两次再跑同一检查：
  - 改回旧的“只在 `changed` 时重绘”条件，检查在“失焦后同版本补画”处失败；
  - 去掉团队/凭证校验，检查在“旧团队的结果被丢弃”处失败。

  这说明新检查确实能抓到这两类问题。临时目录已删除。
- `node --check`（`static/core.js` 和两个脚本）、`git diff --check` 都通过。后端没有改动，本轮没有重跑 Python 单元测试和 TCP 验收。
- 真实浏览器：`scripts/executable_tasks_browser.cjs` 新增两项检查：
  - 点进 AI 指令框后，让队友提交一条不相关的进展，等两次轮询，检查页面没有重绘、“最近同步记录”数没变；

## 修订 3（监理复核 R3）：乱序响应不再让任务版本倒退

问题：监理直接调用真实的 `refresh()` 复现了倒退：同时发出两个读取请求，后发的先返回 revision=3，先发的后返回 revision=2，结果 `state.data.revision` 变成 2，页面依次画了 3 和 2。同一账号、同一团队下，较旧的读取结果覆盖了已经收到的新版本。

做法（只改 `static/core.js`，脚本版本号改为 `20261029-10`；后端、连接器、CSS、服务端 revision 的含义都没动）：

- 页面内给每次读取编一个递增序号（`state.seq`），并记下最近一次采用的序号（`state.applied`）。
- 响应回来时，如果它的序号比已采用的小，说明在它之后发出的请求已经先回来了，这个旧响应直接丢弃，不写入数据也不重绘。判断依据是“发出先后”，不是 revision 大小，所以：
  - 同一版本的正常响应照常采用，R2 的“同版本、失焦后补画”不受影响；
  - 同一版本的强制刷新也照常采用并整页渲染。
- 强制刷新（切页、切队、手动刷新）本身也拿新序号，所以在它之前发出的轮询，晚回来也盖不掉它。`load()`（登录、创建或加入团队后的载入）按同样规则处理。
- R2 的团队/凭证校验保留：换队、退出登录后，旧请求仍然直接丢弃。
- 轮询频率和同步机制都没变，也没有停掉任何必要请求。

验证（都是 Node 中驱动真实 `refresh()` 的检查，只替换网络请求，**不是浏览器实测**）：

- `node scripts/executable_tasks_render_check.cjs` 全部通过。新增 5 项乱序检查，每个请求可以单独决定什么时候返回：
  - **监理复现的场景**：先发的请求挂起，后发的先返回 302，页面画 302；先发的再返回 301，`state.data.revision` 仍是 302，页面只画过 302，没有出现 301；
  - **编辑保护中的两个乱序响应**：AI 指令框聚焦时，后发的 304 先回来，先发的 303 再回来，数据保留 304，且不重绘；失焦后再轮询一次，revision 仍是 304，补画一次，用的是 304；再轮询不重复画；
  - **同版本强制刷新**：仍然整页渲染一次；
  - **强制刷新前发出的轮询晚回来**：盖不掉强制刷新拿到的 305；
  - **切页前发出的旧请求晚回来**：被丢弃，数据仍是切页后的版本。
- 修订 1（展开/收起）和修订 2（保护后补画、换队/退出丢弃、只读不写、轮询从不整页渲染）的检查全部继续通过。
- 反向验证：在临时副本里去掉序号判断，检查在“先发请求晚回来不能倒退”处失败；临时目录已删除。
- `node --check` 和 `git diff --check` 都通过。后端没有改动，本轮没有重跑 Python 单元测试和 TCP 验收。
- 真实浏览器：按要求本轮没有再启动 Chrome（之前几轮在沙箱内都以 SIGABRT 退出），**待监理用原生浏览器核对**。

### 修订 3 补充（监理复核 R3 第二次）：按数据版本保证不倒退

上面只按请求编号的做法**不够**：监理又复现了一种倒退，先发的 r1 先返回 revision=3，后发的 r2 后返回 revision=2，结果当前版本变成 2，页面画了 [3, 2]。原因是服务端各线程开始读库的先后，和浏览器发出请求的先后不是一回事，后发的请求也可能读到更旧的数据。

现在的规则（仍只改 `static/core.js`，脚本版本号改为 `20261029-11`；后端 revision 规则不变，按约定把它当作递增整数）：

- `state.data` 旁边记下它属于哪个上下文（`state.dataCtx` = 登录凭证 + 团队）。新函数 `adopt()` 在同一上下文里比较：
  - 新响应的 revision **更低**：一律丢弃，不管请求是先发还是后发；
  - revision **相同**：只有比已采用的那次发出得更晚才采用（请求编号只在这时用来定先后），所以 R2 的“同版本、失焦后补画”和同版本强制刷新都照常；
  - revision **更高**：采用。
- 换团队、重新登录后，上下文不同，不拿旧团队或旧账号的 revision 来比，新上下文的第一份数据直接采用。
- 强制刷新（切页、切队、手动刷新）即使拿到的 revision 比手上的低，也照常整页渲染，用的是手上那份更新的数据，页面不会卡在“正在读取”。
- 响应被丢弃时，编辑保护的补画判断照常进行：失焦后即使这次轮询读到了旧数据，也会用手上更新的数据补画，不必再等下一轮。
- 保留团队/凭证守卫，并补上两处同类问题：
  - `refresh()` 的错误：如果已经换了团队、退出登录，或者有更晚发出的请求已经成功，就不再显示“同步中断”或弹出提示；
  - `load()`：返回时团队或凭证已变，结果和错误都不用到新上下文；
  - `api()` 收到 401 时，只有请求发出时的凭证仍是当前凭证，才会退出登录，旧凭证的 401 不会把新登录踢掉。

### 修订 3 补充二（监理复核 R3 第三次）：`load()` 读取身份前先锁定上下文

问题：上一节写的“`load()` 返回时团队或凭证已变，结果和错误都不用到新上下文”**当时并不成立**。`load()` 第一句 `state.me=await api('/api/core/me')` 在等待之前没有记下身份。监理直接驱动真实的 `load()` 复现：old-token 和团队 A 发起 `load`，期间切换成 new-token 和团队 B（`state.me` 已是 new-user），这时旧的 `/me` 才返回 old-user 和团队 A。结果当前用户变回 old-user，当前团队变回 A，并且开始请求 `/api/core/teams/A`。

做法（仍只改 `static/core.js`，脚本版本号改为 `20261029-12`）：

- `load()` 在发 `/me` 之前就锁定三样东西：本次的登录凭证、当时选中的团队、本次 load 的代次（`state.loads`，每次 `load()` 加一）。
- `/me` 返回后先核对：凭证仍相同、没有更新的 `load()` 开始过、选中的团队没被切换。三项都满足，才写 `state.me`、选择团队、发团队请求；否则直接结束，不写任何状态、不发后续请求、不渲染。`/me` 出错时也一样：上下文已失效就安静丢弃，仍有效才照常把错误抛给登录表单显示。
- 团队数据那一步同样同时核对代次、凭证和团队，再按修订 3 补充里的 `adopt()` 规则采用。
- 正常登录不受影响：没有记住的团队时选第一个团队；记住的团队仍在列表里就继续用它；没有团队时 `state.data` 为空。没有禁用 `load()`，也没有通过清空新用户已选团队来规避。

## 一、契约

现有核心任务里没有与之等价的字段：`acceptance` 是检查方法，`depends_on` 与 `source_ids` 是依据，旧版 `/api/projects` 里的 `deliverable` 不在核心流程中。因此新增一个嵌套对象，原有六个字段不变，也不重复建第二套依据或验收字段。

```json
{"key":"T1","title":"验证姓名接口","owner_id":"成员ID","acceptance":"怎样检查","depends_on":[],"source_ids":["direction"],
 "execution":{"tool":"终端","steps":["按团队已有启动说明启动后端","发一次正常姓名请求","发一次空姓名请求","保存两次实际返回"],
              "ai_prompt":"目标…已知依据…边界…产物…验收…（非AI任务为空字符串）",
              "deliverable":"两次请求的实际返回原文","help_hint":"写明卡在哪一步并贴出报错原文，向队长求助"}}
```

后端校验（`app/team_core.py` 的 `validate_plan` 内）：

| 字段 | 规则 |
| --- | --- |
| `execution` | 必须是对象，并且恰好包含这五个键；缺少或多出任何键都拒绝 |
| `tool` | 非空文字，不超过 120 字 |
| `steps` | 字符串列表，1 到 8 条；每条非空且不超过 300 字；不能重复；不能有一条与任务标题完全相同 |
| `ai_prompt` | 文字，可以为空，不超过 2000 字 |
| `deliverable`、`help_hint` | 非空文字，各不超过 400 字 |

- 所有说明文字都会经过现有的密钥脱敏（`scrub`）。
- 不合格时返回 `502 invalid_execution`，错误信息说明哪项任务缺了什么，并写入 `last_error` 显示在网页上。草案不保存，活动计划和上一份草案都保持原样。
- 原有校验都没有放宽：未知成员、伪造引用、循环或未知依赖继续拒绝；空 `tasks` 的含义也不变（仍然可以生成，确认后表示清空当前任务）。
- 这些校验只检查形式，**不能证明说明在语义上正确**。比如一条步骤写得空泛但不完全等于标题，就能通过。
