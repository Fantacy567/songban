# 松伴用户全流程体验汇总报告

日期：2026-10-31（北京时间）。基线：`df463269b0cbb3d8851f8240a95b10e818eb0007`，分支 `feat/material-intake`。

后续结果见[修复与复验报告](用户全流程体验修复与复验-2026-10-31.md)。本文件保留修复前的结论；真实短信配置按用户要求跳过，不能视为已解决。

## 结论

**五个独立会话均从游客入口走到交接、复盘和退出重登续做。短信与模型使用测试替身时，松伴的应用内协作闭环可以完成；正常本机服务的新用户入口仍被短信配置阻断。流程能够走通，但前半段和续做入口还不够顺。**

指引最有效的是任务阶段：确认草案后，页面能告诉用户先做哪项、等谁、检查谁、何时核对交付。最需要改善的是个人材料和私人讨论转入团队、共享后的目标跳转，以及重登后找回当前阶段。

当前优先处理三项：**正常服务无法注册、共享记录入口进入错误空间、登录后未保存材料刷新丢失**。其次改善个人/团队历史提示、会话标题、摘要署名和状态文案。

这里的“闭环”指实际写出的文字成果经过另一登录身份检查，能够导出交接清单、保存复盘并继续操作。没有制作真实参赛软件、进行真实演示或向主办方提交。不能把本报告当作真实短信、模型质量、作品质量或线上部署验收通过。

## 本轮如何执行

用户要求每个会话都从头到尾体验。因此五个会话执行相同的完整链路，仅人物和设备不同，没有按模块分工：

游客活动 → 注册 → 个人材料 → 私人讨论与历史 → 创建小队及第二账号加入 → 共同方向 → 显式共享 → 队长统筹和确认任务 → 两人成果与依据 → 相互检查 → 交接导出 → 复盘 → 退出重登并续做。

- 每个会话独立使用两名合成人物、两个浏览器上下文、自己的空数据库与服务端口，共 10 个测试账号、5 个团队。账号与团队均通过页面创建，业务写入通过表单和按钮完成。
- 使用 Windows 上的真实 Edge 浏览器引擎，由 Playwright 操作、读取可见 DOM 并保存截图。手机会话全程保持 390×844 触屏模拟，没有切换桌面完成关键步骤；它不能代替实体手机、软键盘和 iOS Safari 测试。
- 五个会话开始探索时不读业务源码、旧 E2E 或隐藏接口找路。完成后由本汇总会话查阅源码、截图和只读数据库，复核报告中的事实。
- 正常服务 `http://127.0.0.1:8893` 仅进行游客浏览和只读状态检查。所有注册、模型调用及业务写入均在 `8901`—`8905` 隔离环境。没有发送真实短信、调用付费模型或修改正常账号数据。
- 隔离环境中的验证码明确标注未发送短信；整理、讨论、统筹使用固定样例。固定回答与部分人物题材不匹配属于测试替身限制，没有算作真实模型缺陷。隔离服务的短信状态仍报告底层未配置，是已说明的测试条件。
- 这是 **5 次 AI 代理模拟体验**，每次由同一代理扮演两种身份；不是 5 名真人研究，也不是 10 名独立专家的质量评价。不据此计算真人成功率或满意度。

本轮是新用户旅程审查，没有重跑全仓单元测试，也没有修改产品业务代码。本轮新增的 `scripts/ux_review_server.py` 仅用于这五个本机隔离测试服务。

5. **经常被打断的用户，1280×800，8905。** 完成全链路，额外验证一次模拟超时后的核对与新尝试、共享草稿恢复、进展跨页面恢复和重登续聊。已保存内容仍在；登录后的未保存材料刷新丢失，重登默认空团队会话也增加续做成本。[会话 5 完整报告](用户全流程体验-2026-10-31/session-5.md)。

各会话均是在**替身环境内凭可见 UI 找路走通**。正常 8893 的注册阻断没有被跳过后算作正常服务成功。所有会话都实际到了导出、复盘和重登续做阶段，没有把未跑环节写成完成。

汇总会话另以只读 SQLite 连接核对了五个数据库：每个均有 2 名账号、1 个团队、正式计划 v1 的 2 项任务、2 份带依据的完成报告及 2 次通过检查；每次检查人的账号均不同于该成果作者，并有检查说明。五个目录均存在实际下载的交接清单和已保存复盘。结构核对支持记录已落地，不能代替对成果质量的独立评价。[最终记录核对](evidence-user-journey-2026-10-31/final-state-verification.json)。

## 应保留的体验

1. **先个人探索，再主动选择共享。** 无需先组队即可收集材料、讨论；共享前能选团队、改摘要、核对原提问和来源，其他回合仍属于本人。改进衔接时应继续保留这些确认。
2. **正式任务后的下一步明确。** 负责人、前置依赖、完成依据、另一成员检查以及交付核对形成了连续指引。用户能从任务卡直接同步进展或检查同伴。
3. **完成、检查和正式收件有清楚边界。** 自报完成不会直接变成检查通过；导出包含实际报告和检查依据；交付页继续提示演示需实测、主办方收件未知。
4. **已保存记录可以续做。** 五次体验均找回已保存的方向、任务、检查和复盘；个人历史也可恢复。中断会话验证了未知结果不自动重发、共享摘要恢复和进展草稿跨页面恢复。

## 问题、复现与建议

以下 P1 表示应优先修复的入口阻断、错误跳转或输入损失；P2 表示可绕过但明显影响理解和续做；P3 表示局部反馈改进。会话编号表示本轮观察来源，不代表真实用户发生比例。

### UX-01 · P1：正常本机服务的新用户注册未就绪

**复现：** 8893 活动页 → 登录 → 第一次来注册。页面提示“短信服务尚未配置，暂不能注册或使用验证码登录”。12:14 的只读状态为 `ready=false`、`configured=false`、`delivery_verified=false`；同一服务健康检查正常。

**影响：** 没有已有账号的人不能进入需登录的资料保存和团队流程。当前明确报错本身是正确的，但出现得较晚：游客可以先写长段材料，再发现不能注册。此次没有请求真实短信，因此应表述为配置与 UI 表明不可用，不能声称测得短信投递失败。也未检查 GitHub 部署或其他线上环境。

**建议及验收：** 使正常启动进程获得所需配置，并完成一次真实收码、注册和密码重登验证；不要用隔离测试码验收。未就绪时在游客保存入口提前说明限制。凭据存在 GitHub Secrets 中，并不能证明当前本机进程已读取它们。

来源：全部五会话及汇总只读复核。[注册提示截图](evidence-user-journey-2026-10-31/normal-registration.png)、[运行状态](evidence-user-journey-2026-10-31/normal-runtime-status.json)。

### UX-02 · P1：共享成功后的查看入口未进入接收团队

**复现：** 已有团队，在个人空间打开某轮回复 → 选择内容共享 → 选团队并确认 → 查看团队记录。URL 进入 `#/library`，空间却仍为“我的个人空间”，主体显示创建/加入小队表单。手动切目标团队后才能看到刚共享的记录；“查看已共享记录”也能出现同样问题。

**影响：** 核心交接动作已经成功，但成功入口像是在要求用户重新组队，容易被理解成共享失败或团队丢失。实际记录仍存在，有可见手动绕行办法。

**建议及验收：** 成功入口使用该共享回执对应的团队和记录，进入后定位目标；普通共享历史入口若目标不明确，就让用户选择已加入团队。验证个人空间向两个不同团队分别共享，查看时均进入正确范围，同时不额外公开私人回合。

来源：会话 4、5。汇总核对 `ShareTurnPreview.tsx` 仅调用 `onNavigate('library')`，外壳导航没有携带共享目标团队，与现场现象一致。[错误落点](evidence-user-journey-2026-10-31/s4-shared-record-wrong-scope.png)。

### UX-03 · P1：登录后的未保存材料刷新丢失，提示不足

**复现：** 已登录，在资料入口保存一份材料后，再输入另一段补充但不保存，刷新页面。已保存原件仍存在，新输入变为空。登录后没有游客态那句明确的“刷新会丢失”，仍显示“当前输入先留在本页；登录后保存至个人空间”。

**影响：** 被打断者需要重写；这里丢失的是尚未保存的输入，不能写成已保存材料丢失。进展表单跨页面能保留输入，资料入口缺少相应保护，让同一产品的保存预期不一致。

**建议及验收：** 提供按当前用户和资料空间隔离的草稿恢复，或离开/刷新前明确告知未保存；显示准确保存状态。验证已登录资料输入刷新、导航回来后可恢复或得到明确预警，另一账号不能读到前一账号草稿。退出和切换账号仍应保持隐私清理边界。

来源：会话 5，含汇总要求追加的直接对照：刷新前输入值非空，刷新后为空，已保存材料前后均为 2 份，期间没有提交业务写请求。[对照 JSON](evidence-user-journey-2026-10-31/s5-draft-refresh-comparison.json)、[刷新前](evidence-user-journey-2026-10-31/s5-draft-before-refresh.png)、[刷新后](evidence-user-journey-2026-10-31/s5-draft-after-refresh.png)、[进展恢复正面参照](evidence-user-journey-2026-10-31/s5-progress-draft-restored.png)。

### UX-04 · P2：个人探索转团队、重登续做时，原内容和当前阶段不明显

**复现：** 在个人空间存材料、讨论后建队，进入空方向表单；再到团队工作台，只显示空会话。完成任务和复盘后退出重登，也默认进入没有团队会话的工作台，主要按钮仍是“开始一段讨论”。切回个人空间可找到旧讨论，任务和复盘也在。

**影响：** 用户需要理解“团队范围中的本人私聊”和“个人空间私聊”是两套历史，且自己拼出上次做到哪一步。没有证据表明历史丢失，也不能以自动共享私人内容来解决问题。

**建议及验收：** 空状态明确解释范围，并提供“继续我的个人讨论”；建队后提供选择已有材料/摘要的入口，仍经本人预览确认。工作台可提示“已有 2 项任务检查记录，继续核对交付”，并恢复最近访问阶段。验收从个人讨论建队、以及交接后重登两种路径，都能就近找到原内容和当前动作。

来源：全部五会话。[重登空团队会话](evidence-user-journey-2026-10-31/s5-relogin-empty-team-discussion.png)。

### UX-05 · P2：历史会话同名，无法凭内容辨认

**复现：** 同一分钟创建一段讨论并发送问题，再创建第二个空会话。历史选项均显示“新的项目讨论 · 10/31 12:05”，需要逐个打开区分。

**建议及验收：** 有内容后使用首问摘要作为标题，空会话标“未开始”，提供重命名；时间作辅助信息。连续创建两个不同主题及一个空会话后，桌面和 390 像素窄屏均能辨认，重登后保留。标题不能因此暴露给其他成员。

来源：会话 2、3。[手机历史截图](evidence-user-journey-2026-10-31/s3-duplicate-history-titles.png)、[历史与设备记录](evidence-user-journey-2026-10-31/s3-device-and-history.json)。

### UX-06 · P2：人工编辑摘要在接收端像是模型原话

**复现：** 将“本人编辑摘要”整体重写，再共享。队友资料库却用“模型名称：回复关键信息”解释内容，并以 `ux-review-sample：` 引出人工改写文字。

**影响：** 发送端说明原助手回复不自动共享，接收端的作者表达却容易让人误认为正在看模型原答。本问题与测试模型的回答质量无关。

**建议及验收：** 展示“某某编辑的共享摘要”，另列原提问、原回复的模型来源及测试标识。用明显不同于原回答的摘要验证接收端和导出，均能区分编辑者与模型来源，也不把未选择的原回复全文带入团队。

来源：会话 1、2、4、5。[接收端截图](evidence-user-journey-2026-10-31/s4-edited-summary-attribution.png)、[对应页面文本](evidence-user-journey-2026-10-31/s4-edited-summary-attribution.txt)。

### UX-07 · P2：几处状态文案比实际记录更确定

本轮观察到三个独立分支，应分别修正和验证：

- **无前置依赖被说成已有检查。** 首次发布后，T1 无依赖、0/2 成果检查，下一步却说“它的前置成果已有检查记录”。应改为“没有前置依赖，可以开始”；有依赖且确已通过时再使用当前解释。五会话均观察到。[现场截图](evidence-user-journey-2026-10-31/s3-no-dependency-task.png)。
- **填写未知也被说成已有原文。** 将赛事要求和评分填“未知、未取得原文”，交付仍说“已保存原文和评分依据”。后文要求核实是有益的，但不能消除前半句的误导。应至少改成“已填写说明”，需要表达已有正式原文时采用明确来源状态。会话 1、3、4 观察到。[交付文本](evidence-user-journey-2026-10-31/s4-delivery-final.txt)。
- **首次保存方向也提示已有草案。** 当前并无草案，却提示已有草案要重新统筹。应区分“还没有草案，可开始生成”和“已有草案需重新核对”。会话 1、4 观察到。

汇总查阅 `app/core_workflow.py` 确认前两项属于规则生成的界面文案，不能归因于固定模型回答。验收应覆盖无依赖、有未完成依赖、依赖已检查、未知赛规、已有赛规、无草案及已有草案等真实状态。

### UX-08 · P2：建队和方向保存的就近下一步弱，帮助未覆盖个人工作台

**复现：** 创建小队直接到方向页，要回“小队”页找邀请码；保存方向后没有清楚的邀请、继续讨论或生成分工入口。帮助弹窗从“了解活动，创建或加入小队”讲起，没有介绍无需先建队的个人工作台路径。

**建议及验收：** 建队成功显示可复制邀请码及下一步；方向保存按当前记录给一个明确主动作。更新帮助，把“个人收集与讨论 → 选择共享 → 队长确认 → 执行与互查”串起来。保留现有“活动/实践”入口，并把任务页已有效的阶段指引延伸到前半段与重登落点。

来源：会话 1、2、4 的绕路，其他会话也实际回小队页取邀请码；汇总独立核对了正常帮助内容。[帮助截图](evidence-user-journey-2026-10-31/normal-help.png)。

### UX-09 · P2：非技术用户的输入成本与团队资料说明可改善

**观察：** 日期字段示例是带时区的 ISO 字符串，成果/检查示例主要讲请求返回 200；方向标题围绕“智能体”，个人工具页展示 MCP、Python 和配置项。注册填过的“这次想尝试什么”，入队后又要求填写“本次意愿”，用途差异没有解释清楚。

**建议及验收：** 日期采用选择器并显示时区；提供文字、设计、讲稿、软件等不同成果的检查示例。个人工具首屏说明可继续用网页同步。解释个人简介和当前小队意愿的区别；若提供带入初稿，应由本人确认后共享。让不会编程的人可以提交有效的文字成果和依据，而无需先理解工具配置或 HTTP 状态码。

来源：会话 2 的完整非技术旅程，以及会话 1、3、4、5 的相关观察。本轮没有因为日期格式而提交失败，故不将此写成输入功能故障。[方向表单](evidence-user-journey-2026-10-31/s2-direction-form.png)、[个人工具页](evidence-user-journey-2026-10-31/s2-personal-tools.png)。

## 建议的修复顺序和复验要求

**第一批：让新人能进入，关键动作有可靠结果。** 处理 UX-01、02、03，分别复验正常服务真实验证码、共享到正确目标、材料未保存输入的保护。短信配置需要在实际启动环境验证，单独修改提示或通过测试替身不能关单。

**第二批：让“整理思路、组织项目”成为连贯体验。** 处理 UX-04、05、08、09：工作台承接个人资料、已有讨论和当前团队阶段；标题可以辨认；建队/方向保存后有下一步；普通用户有合适的成果示例。建议沿用现有“活动/实践”两入口，把精力用于这些衔接点。

**第三批：让用户正确理解当前事实。** 处理 UX-06、07、10、11：摘要归属、真实状态分支、跨账号刷新和异常核对反馈。文案修复虽小，也应以对应状态复验，避免统一换一句话又误导另一分支。

修复后的整体验收应继续让每个体验者独立走完整链路，并特别覆盖以下条件：

- 从无账号开始；个人讨论后才建队；共享目标与当前空间不同；同一分钟多条讨论。
- 未保存材料中断后返回；两账号交替交成果；首次无依赖任务；赛规未知；退出后继续上次阶段。
- 390×844 的全流程，随后补一次实体手机的键盘、弹窗和下载体验。
- 保留本人私聊、显式共享、队长确认、另一成员检查的边界。仍不以交接清单或内部检查替代主办方收件证明。

新增回归应验证真实外壳中的跨空间导航和输入恢复；仅检查按钮有回调或后端返回 200 不足以覆盖本轮问题。真实模型效果需另选有依据的项目材料，检查是否理解个人目标、正确引用、给出可执行下一步；本轮固定回答不提供这方面证据。
