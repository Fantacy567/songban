## 4. 已确认的软件问题

P1 表示阻断关键使用路径或可能将错误依据带入正式流程，应在完整验收前处理；P2 表示有绕行方式的功能/兼容问题。以下优先级是本报告的修复建议。

### BUG-01 · P1 · 团队收到的共享草稿不可见【新增回归】

**复现：** 用户在个人资料空间保存文字→读取→整理→选中条目共享到一个尚未生成整理结果的团队→打开团队“资料入口”。

**实际：** 团队接口已返回 `drafts.length=1`、一份已读取来源，但 `result.items` 不存在；页面“已保存的团队草稿”标题和继续使用按钮均为 0。共享已保存，接收方却无法从界面接续。

**预期：** 已收到的草稿应独立于团队是否运行过模型整理而可见，并能继续核对和使用。

**原因/位置：** `static/songban-materials.js:59` 在没有 `result.items` 时提前返回；草稿展示位于后续同一渲染流程中。团队共享只复制选中的来源与草稿，不会同时创建团队模型结果。

**影响：** 首次跨个人→团队交接中断；让队长再运行一次模型整理才能看到草稿增加了不必要的前提，模型未配置时更无法绕行。

**建议与验收：** 单独渲染草稿区；增加“空整理结果＋已有共享草稿”的接收方浏览器用例，在模型不可用时仍可打开草稿。证据：[browser-gaps.json](evidence-full-audit-2026-10-31/browser-gaps.json)、[现场截图](evidence-full-audit-2026-10-31/missing-shared-draft.png)。

### BUG-02 · P1 · 同一团队人工纠正后，旧草稿仍无提示通过【新增回归】

**复现：** 在团队资料空间整理条目→生成方向草稿→在同一空间人工修改并确认条目→携带最新空间 revision 调用旧草稿 `/prepare`。

**实际：** 返回 HTTP 200。草稿仍是“材料表述：提交时间尚未确认。【样例】”，当前条目已经改成“同团队人工纠正：请勿使用旧条目”。

**预期：** 使用旧草稿前识别所选条目已变更，要求重建或明确展示历史差异并再次核对。不能只因原始文件未变化就默认草稿内容仍有效。

**原因/位置：** `app/materials.py:487` 的 `prepare_draft` 校验当前请求 revision 与引用来源文件状态/版本，但没有比较草稿内条目与当前已纠正条目的版本或内容。

**影响：** 过时内容可重新进入方向编辑页或团队讨论；正式方向仍需人工保存，不能说它会自动覆盖，但此前人工纠错没有形成完整保护。

**建议与验收：** 草稿记录条目版本或内容指纹；同团队条目变化后提示并阻止静默复用。个人→团队共享本来就是独立副本，不要求跨空间自动覆盖；本问题的关键证据是**同一团队空间内**的修改。见 [core-closure.json](evidence-full-audit-2026-10-31/core-closure.json) 的 `same_team_draft_after_human_edit`。

### BUG-03 · P1 · 新增资料依赖没有进入默认 CI/容器安装链【新增回归】

**复现：** 创建不继承系统包的新虚拟环境→仅安装 `requirements.lock.txt`（当前 CI 命令）→执行 `MaterialsTests.test_real_txt_docx_and_pdf_parsing` 和 `test_partial_pdf_failure_keeps_successful_pages`。

**实际：** 两项均 ERROR，分别 `ModuleNotFoundError: No module named 'docx'` 与 `No module named 'reportlab'`。

**预期：** 仓库声明的安装步骤足以运行启用的新功能及默认全量测试，不依赖开发机已有包。

**原因/位置：** `.github/workflows/python-package-conda.yml:21` 仍只安装基础锁文件；`Dockerfile:5` 只安装 `requirements.txt`。资料依赖另列在 `requirements-materials*.txt`，未被这两个入口引用；`reportlab` 被新增测试和 QA 样本生成器使用，但也未列入资料依赖文件。

**建议与验收：** 明确运行依赖和测试依赖，将 CI、容器及安装文档接到相应文件；至少在干净 Windows 和 CI Linux 环境跑通全量及实际解析/OCR 样本。当前 Windows 资料锁文件不能未经验证直接当作 Linux 锁文件。见 [clean-materials.txt](evidence-full-audit-2026-10-31/clean-materials.txt)。

### BUG-04 · P1 · 原生插件注册成功，当前 Codex 宿主实际不加载【既有功能/本机兼容】

**复现：** 在临时 HOME 安装原生连接器，再使用真实 CLI 宿主检查器读取加载结果。没有写用户实际 Codex 配置。

## 5. 测试工程问题

### TEST-01 · P2 · Windows 符号链接与权限测试未按平台验证

两个测试在创建符号链接时就因缺权限退出，故尚未证明该环境下能拒绝链接逃逸。两个 UTF-8 重跑断言用 Unix `0600` 比较 Windows 文件模式，实际为 `0666`；ACL 是否足够严格尚未验证。应在具备条件的平台执行真正的链接攻击用例，并对 Windows 使用 ACL 验证；无法执行时明确标记原因，不能改为无条件通过。

### TEST-02 · P2 · 四个旧 E2E 脚本硬编码个人 macOS 路径

四个 `core_*_e2e.cjs` 文件的 Playwright 引入依赖 `/Users/ben/...`，本机直接启动均失败；还存在 `/private/tmp`、浏览器或旧页面入口假设。应统一使用可配置运行时、临时目录、可配置 QA 地址和当前选择器。现有统一前台浏览器通过不覆盖原生插件安装/选中对话上传等专用路径。

### TEST-03 · P2 · 用例重复发现且新共享场景覆盖不足

`tests/test_materials.py:15` 直接导入 `CoreTests`，造成 27 次重复执行；不是新增 27 个独立覆盖点。资料专项与现有浏览器全部通过仍未发现 BUG-01/02，说明缺少“接收方空结果空间”和“草稿创建后人工纠正”的状态组合。建议避免暴露导入的 TestCase 类，并为这些状态补针对性断言；不要单看用例数量作为覆盖率。

## 6. 核心闭环判断

### 6.1 已跑通的协作子闭环

在“至少两名成员、可以生成有效统筹草案、使用网页或可工作的通用 MCP”前提下，本轮实测链路是：

1. 注册/登录（短信 fixture；密码使用真实服务端验证）。
2. 建队、另一名成员入队、保存共同方向。
3. 同步带来源的进展，保留不同观点，生成建议草案。
4. 队长确认后才产生正式任务；个人工具领取本人任务和共同方向。
5. 成员提交成果，队友退回，重交后队友验收；前置依赖随实际验收推进。
6. 导出交接说明、保存团队复盘，并从持久化记录重新读取状态。

证据来自 [core-closure.json](evidence-full-audit-2026-10-31/core-closure.json)、[mcp-loop.json](evidence-full-audit-2026-10-31/mcp-loop.json) 和两套浏览器结果。这里证明的是协作状态流转，不证明合成“成果”真实达到某场比赛标准。

### 6.2 仍有的闭环缺口（不是全部属于本次新增 bug）

**GAP-01：真实短信入口未就绪。** 正常服务返回 `ready=false`、`configured=false`、`delivery_verified=false`；缺少阿里云 AccessKey、签名和模板配置。浏览器注册/短信登录通过仅代表协议流程。没有给真实人员发送短信。需配置后以授权测试号码验证送达、登录和错误恢复，当前真实短信注册不能签收。

**GAP-02：单人小队无法完成现有同伴验收规则。** 界面允许“先自己开始”，单成员团队能创建计划并报告完成，但自己验收返回 403 `peer_required`，后续依赖仍等待 T1。这是单人模式与验收策略的衔接缺口。可邀请第二名成员绕行；产品需明确外部评审/可信检查或仅记录个人完成的状态，不能简单把自报等同同伴验收。

**GAP-03：无模型时没有新的正式计划生成出口。** 明确模拟未配置时 `/review` 返回 503 `model_not_configured`；进展仍保存，但当前 API/页面没有手工创建完整计划草案的入口。忠实报错是正确行为；若产品要求模型故障时继续分工，需要补充人工草案并保留确认权限。正常服务本次真实模型可用，这里是故障/未配置分支。

**GAP-04：活动到团队没有完整业务关联。** 活动目录为已标注样例。已有团队用户从另一个活动点“创建或加入小队”会进入当前旧团队；再点“创建或加入另一支小队”可以打开创建表单，**不是无法创建团队的硬阻断**。缺少本次活动与团队关系、规则快照/有效来源及独立报名状态，不能把导航跳转当作报名闭环。

**GAP-05：交付核对不等于正式提交。** 交付页可以查看检查状态和导出交接说明；当前页面没有独立的文件提交/正式回执表单，服务端 `submission.state='unknown'`，明确提示未读取主办方收件状态。团队报告可记录链接，但本轮未发现正式提交回执对象、核验状态与回执闭环。若提交在平台外完成，也需可追溯的提交人、版本、时间和真实回执；不得伪造官方确认。

**GAP-06：复盘目前是团队共享报告。** `reflection-form` 提交到 `/api/core/teams/{id}/reports`，另一名成员确实可见；界面已提示团队可见。这不是个人私密档案，也不是规划中的独立赛后访谈/成长报告链。该克隆未验证到这些新能力，不能将一个复盘文本框当作全部实现。

另外，仓库现行规划仍包含家庭 AI 学习产品目标。当前 `/api/learning/v1` 存在样例活动和体验会话接口，并非没有任何实现；但本轮代码清单和流程未显示家庭关系/受限学习者身份、版本化课程与掌握判定、受控实验额度、家长报告和课程权益的完整链路。它们属于已声明的待实施规划，**团队协作测试通过不能证明家庭学习或商业闭环已经完成**。

### 6.3 最终验收判定

- **资料输入到正式协作：未完全闭环。** 解析和整理可用，共享接续与纠错后草稿有效性存在 P1 问题。
- **双人网页/通用 MCP 协作：有条件跑通。** 提交、退回、重交、同伴检查及持久化有实证。
- **当前机器原生 Codex 连接器：未闭环。** 实际宿主加载失败。
- **单人、模型不可用、真实短信路径：未具备同等完成能力。** 需要产品出口或环境配置。
- **完整比赛交付/个人成长链，以及规划中的家庭学习链：未闭环。** 缺失项应按计划建设，不应把未实现部分写成测试通过。
- **可交付质量门槛：未通过。** 全量失败和干净安装失败仍未消除。

## 7. 修复与复验顺序

1. 修复 BUG-01/02，并补接收方、同空间修改后的草稿回归；保留既有来源、权限、撤回与并发保护。
2. 修复 BUG-03，使干净安装、CI、部署依赖一致；在目标操作系统验证 OCR 和文档解析。
3. 修复 BUG-04/05，分开验证原生宿主加载、真实同步回执、重装保留配置，以及 Windows 文件访问权限。
4. 修复 BUG-06 和测试工程问题，重跑受影响场景，再运行全量；准确统计独立用例，不以专项代替全量。
5. 为单人、无模型、活动关联、正式回执和个人复盘定义可验收出口；真实短信另做授权送达验证。

在这些问题关闭前，可以用于受控的双人协作演示，但不应宣告“全项目全量测试通过”或“核心业务已经全部闭环”。
