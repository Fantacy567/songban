## 1. 工作台要解决什么

松伴已经能保存资料、整理引用、确认共同方向、发布任务、同步成果并由同伴检查。工作台把这些能力连接为连续的操作过程：用户带着问题和材料进入，与 AI 讨论，保留草稿，决定哪些内容要成为团队共同记录。

主要产出是可理解的目标、范围、待确认问题、任务建议和可交接的记录。用户不需要先安装个人工具，也不需要先学会挑选专员。编程、终端执行和自动制作网页不纳入这次融合；既有外部个人工具连接继续承担用户在其他工具中的工作衔接。

源项目的工作台适合提供交互基础，松伴现有业务提供事实与确认流程。不能把源项目的赛事报名、主办方管理、评审权限或完整数据库连同工作台一起搬入。

## 2. 入口与页面结构

一级导航保持“活动／实践”。实践继续使用 `#/work`，页面名称调整为“项目工作台”；现有 `#/collaboration` 保留兼容，不另建一个独立的“AI”一级入口。

当前 `#/work` 和 `#/collaboration` 都映射到 `overview`，现有“任务”页还承载团队进展、统筹建议和已确认任务。实施时升级这个入口，保留任务面板及深链可达性；不能直接替换后让已确认任务或待确认计划消失。

页面分工：

- 顶部：当前个人／团队范围、共同目标、当前下一步，以及查看方向或切换团队的入口。
- 主区：个人讨论、资料引用、可编辑草稿和待确认动作。对话默认属于本人。
- 辅助区：本次采用的资料、本人任务、已共享记录和历史会话。窄屏改为可展开区域。
- 团队操作：沿用方向、任务、资料库、成员、交付与复盘；“个人工具”继续管理外部连接。

不增加第二条网站侧栏，不复制源工作台中的“参与／主办／平台”整套导航。主界面使用松伴现有暖米白、紫色和语义 tokens；源工作台的蓝色 DSH 视觉不能作为新的全局皮肤。

无团队时允许整理个人材料和讨论想法；用户想共享或正式组织协作时，再进入既有创建／加入小队流程。用户尚未加入团队，页面不显示虚构队员、任务或共同方向。

## 3. 一条完整的使用过程

以用户已有一份比赛说明、想做一个校园失物招领助手为例：

1. 从活动页收下比赛材料，进入实践。原文件和 OCR／文本解析继续由资料入口处理。
2. 点“帮我理清想法”。助手说明这次读取了哪些材料、哪些条件仍未知，再帮助缩小目标。
3. 讨论得到方向草稿。用户可以编辑、留在个人会话，或选择团队后预览共享。
4. 队长在原共同方向表单中核对并保存，使用当前 `expected_revision`；普通成员只能提出建议。
5. 需要分工时，先把选中的讨论保存到团队记录，再由队长显式发起原有团队统筹。计划仍是待确认草案。
6. 队长确认计划后，工作台显示来自正式计划的本人任务。新的聊天建议不会直接改写任务。
7. 用户完成一轮工作，编辑并分享必要的结论或进展。团队总智能体可以据此再提建议；本人报告完成和同伴检查仍分别进行。

这条流程的验收重点是“讨论结果能被理解、选择、确认和交接”，而不是聊天消息数量或专员数量。

## 4. 松伴专用的助手分工

### 个人助手

按本人和当前空间保存会话。可以读取本次选择的个人材料，以及当前有权访问的团队方向、本人任务和已共享材料。聊天不会自动广播给队长、队友或未来的家长账号。

第一版提供三个任务型入口：

- **理资料**：解释原文、标出冲突与未知、引用资料段落，保留样例和 OCR 待核对标记。
- **想方向**：澄清要解决的问题、预期产出、时间和明确不做的事，形成待确认方向草稿。
- **排下一步**：根据已确认方向、本人任务和依赖提出建议，指出先要解决的阻塞。

它们是不同的职责与上下文配置，可以使用同一个模型。第一版每次请求只运行用户选择的一种职责，不默认调用多个专员再总结，也不把同一模型的不同提示包装成多模型验证。

成果核对和复盘在后续阶段补充，核对建议不替代同伴验收；个人复盘也不自动变成团队可见内容。

### 团队总智能体

保留松伴现有角色：比较共享记录、识别分歧、提出团队安排。它读取正式团队事实与用户明确共享的内容，计划发布继续由队长确认。

工作台不创建另一套队长、团队成员、任务负责人或任务完成状态，也不把个人聊天直接作为团队总智能体的输入。

**`dsh-chat.ts` 等运行时**：本期保留为参考，模型接松伴现有服务端配置。聊天需独立的请求／输出契约，不能直接调用返回任务计划的 `request_model()` 并把结果当成自由对话。DSH 桌面目录、私人 profile、密钥、数据库和用户历史不复制。

## 6. 松伴接入边界

### 已有事实直接复用

- 账号：`/api/core/me` 与现有 Bearer 认证；工作台不提供旁路注册，短信缺配置仍单独处理。
- 团队：`GET /api/core/teams/{sid}`；工作台只派生展示，不存第二份成员或正式计划。
- 共同方向：`PUT /api/core/teams/{sid}/direction`；只有队长在网页确认，必须带当前版本。
- 材料：`/api/materials` 的个人／团队空间、来源、段落、人工修订和草稿；引用保留来源版本与撤回状态。
- 共享对话：`POST /api/core/teams/{sid}/conversation-notes`；共享前预览，本人确认后复用现有幂等记录与 `capture_only` 行为，不自动触发统筹。
- 团队统筹：现有 `/review` 生成建议、`/proposals/{pid}/confirm` 发布计划；工作台只接入现有人工动作。
- 进展与检查：继续使用 `/reports`、`/my-tasks` 和 `/tasks/{task_key}/check`，不由聊天文字推断已完成或已验收。

共享动作需要新增一个受控的来源适配层：校验所选回答确实属于本人、当前会话与目标团队，服务端取得实际回答和模型标识，再调用抽出的现有共享服务。不能让浏览器自行伪造“已保存的 AI 回答”。人工改写过的摘要须明确标记为本人编辑。

现有共享记录中的“松伴连接器”来源文案也要适配：站内分享标为“松伴项目工作台”，外部工具保留其真实来源；页面和导出都沿用实际模型标识，不把网页讨论冒充某个外部客户端的运行结果。

### 最小新增资源

只新增私人会话、消息、模型请求、候选动作及必要的共享映射。建议资源名为 `workbench_sessions`、`workbench_messages`、`workbench_requests`、`workbench_actions`；不新增团队、正式任务、资料原件或方向副本。

- 会话记录本人、个人／团队范围、状态和版本。团队范围表示采用该团队的上下文，不表示聊天对所有成员可见。
- 消息记录职责、正文、实际模型标识、引用和上下文版本；模型未知时保留未知。
- 请求记录稳定请求 ID、输入指纹、状态、时间和用量。`pending/running/succeeded/failed/unknown` 分开处理。
- 候选动作记录来源消息、当前状态和必要的基线版本；执行回执绑定实际业务记录，重复确认返回已有结果。

建议新增 `/api/workbench` 命名空间，提供会话列表／创建／归档、消息读取／发送、请求状态读取、动作准备／确认。旧 `/api/core` 与 `/api/materials` 保持兼容；新增路由名称和字段在实施前冻结并进入 OpenAPI。

浏览器退出登录或切换身份必须卸载工作台、清除私人展示，并丢弃旧账号或旧团队的迟到响应。模型调用前后都重新检查授权；退队或来源撤回后的内容不得继续自动回传给模型。

## 7. AI 建议怎样成为实际动作

首版只允许四类行为，所有按钮都由服务端允许列表产生：

1. **准备方向草稿**：展示将改的字段和依据，带入原方向表单；用户保存时再验证队长身份和版本。普通成员可以编辑建议并分享，不能直接保存共同方向。
2. **分享选中回合**：预览用户原话、回答要点、来源和目标团队，确认后保存现有对话记录。会话其他内容保持私人。
3. **请求团队统筹**：提示这是一次模型调用，只有队长能发起。先确认需要采用的讨论已共享；统筹仍只生成待确认计划。
4. **打开已有页面**：只跳转到已知的方向、任务、资料、成员、交付或复盘页面，不接受模型提供的任意执行地址。

AI 不直接确认任务、分配成员、标记同伴验收或正式提交。展示“保存草稿”“已共享”“已发布计划”时，分别使用真实后端回执，不把按钮点击或模型一句回答视为成功。

## 8. 迁移前必须修正的源码问题

以下来自当前源码静态核对，不是本轮运行源项目的故障报告：

- **归档失败后仍可能清空会话。** `AiWorkbench.newSession()` 对归档请求的错误执行 `catch(() => null)`，随后仍发清空请求。松伴应以服务端原子“归档当前＋建立新会话”完成；失败保留原会话，不吞错。
- **源归档 SQL 与消息表定义不一致。** `organizer-integration.ts` 的归档分支按 `personal_dsh_messages.user_id` 查询／删除，而迁移 021 的消息表通过 `session_id` 关联用户。不能照搬这段 SQL；归档需绑定本人会话，且不得漏掉事务与并发保护。
- **团队聊天失败时回滚了个人列表。** `send()` 成功前按空间选择列表，但 catch 固定调用 `setMessages`。松伴需按请求所属会话恢复，并保留输入；切换会话不能把迟到的错误应用到新会话。
- **方向卡预填分支不可达。** `charter_fill` 在最后的导航员分支中要求 `space !== null`，但有 space 时已进入前面的团队分支。松伴应统一处理受校验的动作响应，再按权限打开方向草稿。
- **专员消息只更新页面状态。** 工作台专员分支没有像普通会话一样写入统一聊天记录；不能据其他日志存在就宣称刷新后完整恢复。迁移时每条展示消息必须有真实消息 ID 和持久化来源。
- **框架卡存在读后写窗口。** `project-charter.ts` 先读版本、再无条件 upsert；松伴方向修改继续使用已有事务内版本校验，不复制此写法。
- **松伴五秒刷新会重建页面。** 当前 `refresh()` 可能调用 `render()`。挂载 React 后需把工作台纳入组件生命周期：团队快照更新通过 props／事件传递，禁止轮询抹掉正在输入的内容；离开页面时正确卸载。

防跑偏的词面匹配只作为可选弱提示：合理探索也可能没有命中目标词。首版先清楚展示共同目标与明确不做，不把词面命中写成“AI 已判断偏题”。

## 9. 实施顺序与交付物

### 第一步 源码提取与松伴外壳

从复用清单提取组件和展示逻辑，建立来源说明；拟放在 `frontend/workbench/`，产物放 `static/workbench/`。替换 Next.js 导航和源项目 API，接入松伴现有 `#/work` 页面与视觉 tokens。此步只允许显式的展示夹具，不伪装已有模型回复或正式任务。

交付：可构建的组件、挂载／卸载适配器、路由兼容检查和三档响应式验证。保留原任务与团队统筹界面的可达性。

### 第二步 私人会话与真实上下文

新增 `app/workbench.py` 与单独的会话持久化层；从现有核心模块抽出可注入的账号／团队授权与上下文读取服务，供旧路由和新工作台共同使用。避免新模块再次实现一套不同的权限规则。

交付：个人／团队范围会话、读取历史、新会话与归档、来源选择、刷新／重登恢复，以及跨账号／跨团队隔离测试。加入现有 209 项回归测试的同一发现入口。

### 第三步 助手请求与确认动作

接松伴模型配置，新增独立聊天提示与结构化输出校验；请求先持久登记，成功后保存真实消息和动作。进程退出或网络超时后，只读核对请求状态；未知结果不自动重发，不能用换请求 ID 绕过同一未知请求。

交付：三个职责、来源说明、四类受控动作、共享回执、方向冲突保留输入，以及计划生成／确认的旧链路回归。共享来源映射与原有记录在同一事务中保存。

### 第四步 验证完整使用过程

使用隔离账号、数据库和模型夹具跑通第 3 节全流程，再分别记录实际模型联调结果。模型未配置时材料、历史、任务和手工表单继续可用；不生成静态回答冒充 AI。

上线前确认模型预算／限流、单次输入和历史上限、未知请求核对出口与记录保留规则；当前规划不宣称松伴已有源项目的完整费用账本。恢复旧界面只切换入口和静态资源，不删除新会话与已共享业务记录；出现运行中或未知请求时不自动重新发送。

## 10. 验收清单

1. 一级导航仍为活动／实践，`#/work` 与 `#/collaboration` 兼容，已有任务和待确认计划可达。
2. 不建队也能使用本人材料和讨论；进入团队后只采用当前合法可见的上下文。
3. 队长和队员都不能读取他人的私人会话；换账号、换团队和退队均测试迟到响应与撤权。
4. 对话、专员回复、草稿与历史可在刷新、重登和服务重启后恢复。
5. 新建／归档失败不清空旧会话；并发归档与发送不能丢消息或复制消息。
6. 请求重复点击只对应一个运行；未知结果不自动重新调用模型；缺配置和真实失败准确显示。
7. 每个助手显示实际采用的资料范围；引用保留来源与版本，样例、OCR 和未知状态不被提升为正式事实。
8. 编辑个人草稿不改变团队方向；只有队长显式保存且版本匹配时才能改变方向。
9. 只分享选中的回合；重复确认返回同一记录，分享不自动触发团队统筹。
10. 计划必须经过既有队长确认，任务进展和同伴检查仍使用原有接口与权限。
11. 模型回复及来源文本无法执行脚本、任意跳转或扩大可用动作范围。
12. 五秒同步、页面切换和模型失败均保留输入，卸载后没有残余轮询或串会话更新。
13. 使用松伴 tokens；390／768／1440px、长中文、键盘、加载／空／失败／冲突状态均实际验证。
14. 源码复用、模拟测试、真实模型结果与用户试用分开记录；保留来源说明与回退方式。
