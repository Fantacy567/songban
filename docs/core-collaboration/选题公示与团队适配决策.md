# 选题公示与团队适配决策

2026-10-31。按用户要求，选题资料与后续开发资料分开展示；沿用同一份获准共享记录，不复制原始对话、不另建任务状态。

## 参赛流程

1. 成员在 `#/ideas` 公示本人idea：名称、帮助谁解决什么问题、方案及所需能力/时间。本人可修改，全队可看。
2. 成员用自己的Agent推敲可行性，通过连接器选择共享回合，填写discussion阶段与真实idea_id。原生/通用MCP新增songban_get_topic_ideas读取本队真实ID；安装包版本1.1.0。网页也可手动共享并选择本人idea。
3. `#/idea-library` 只展示选题可行性对话，`#/library` 只展示开发/复盘对话。保留真实用户名、模型、原文、成员颜色、检索与历史分页。旧记录不删除，未关联idea的本人对话可在讨论页关联。
4. 每人明确确认本轮提交结束；无独立idea也可确认。新建/修改idea或上传/关联新选题对话后，本人的确认失效，需要重新确认。
5. 全员确认、能力与可投入时间完整、队长填写公开评分维度后，队长点击AI决策按钮。缺失项直接列出，不补造。
6. AI给出各候选的能力匹配、时间可行性、评分维度匹配参考分、具体理由、风险与引用。服务端按能力40%/时间30%/评分匹配30%计算并排序；这是平台讨论权重，不是主办方权重或获奖预测。AI对话不等于已验证可行性。
7. 排名不选择方向、不发任务。队伍讨论后，队长可带入方向草稿，再通过已有方向表单核对保存；原有未保存草稿会保护。

## 事实与范围

- 数据为本人/队长填写，未独立核实。评分维度缺失时阻止分析；主办方未知的评分权重不由AI猜测。
- 只用选题阶段对话，开发记录更新不会污染选题排名。能力、时间、方向、候选或选题证据变化会使旧排名过期。
- 模型需覆盖全部候选且引用真实idea/成员/规则ID；不能把明确属于另一idea的对话当作本idea验证。无效输出记为失败，不发布假排序。
- 分析请求持久化幂等，每队每小时最多5次明确新请求；超时不自动重放。超过上下文处理范围拒绝，不静默截断。
- 逻辑分库使用scope=discussion/project；旧/library API默认all保留兼容读取能力，前台显式限定scope，MCP支持scope与idea_id。
- 候选、确认、关联和排名保存在SQLite；本轮不新增正式任务系统、不实现投票、不把成员自述当能力认证。

## 验收

272项全量测试通过，含分库、关联归属、本人修改权限、缺资料/全员确认门槛、幂等、无效引用、变更过期及不改正式方向/任务。旧链接抽取测试改用固定公网DNS夹具，避免将外部DNS故障混成提取失败；没有放松SSRF约束。

Chrome双身份与实际原生MCP子进程覆盖idea公示、上传关联对话、全员可见、确认后分析、两库隔离、开发更新不污染排名、只填方向草稿，以及390/768/1440。原生/通用连接器资料库长文、筛选、分页、任务状态隔离回归通过。浏览器模型为明确fixture。

另用合成条件真实调用平台模型：简单网页能力、3小时、用户价值/可用性评分下，校园查询小工具排在大型通用平台前；2个候选及引用校验通过。仅为单次合成场景检查，不是排名质量的普遍保证。首次上游超时未生成替代排名；后续显式检查成功。未发送真实短信，未使用真实孩子资料。
